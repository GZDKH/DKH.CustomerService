## Decisions

### D1 — Identity and trusted origin are different authorities

Reuse CustomerJournalPrincipal/OwnerResolver and locked C2 account resolution for every operation, including receipt replay. Authentication supplies issuer/sub, not an AccountId field. Service-only tokens and forged purpose/context do not grant personal access. Resolve origin for creation from an independently authenticated forwarding context bound to the validated personal principal and trusted storefront host; a raw X-Storefront-Id or token azp/client ID alone is insufficient. Normalize all origin-context/header values and reject missing, invalid, duplicate or conflicting provenance before mutation. No fallback to the first header or caller-provided OriginStorefrontId. Malformed/conflicting declared context is InvalidArgument; invalid authenticated provenance is PermissionDenied; an unavailable required producer is FailedPrecondition.

**G1 unresolved producer gate:** existing PlatformGrpcStorefrontContext only reads the first UUID header. Discovery established no Customer-consumable authenticated origin binding. Before implementation admission, parent/coordinator must name the actual producer, principal binding, authenticated caller/ingress proof, allowed storefront source, freshness/replay bounds and owner verification tests. Prefer extending the existing authenticated forwarding/context channel if it can supply those properties. Do not invent a deployed attestation, reinterpret a browser token as a gateway credential, or add credentials/config in this child. If a separately admitted producer is needed, retain this gate and fail closed on creation until it is available. Owner-safe reads/history/delete do not acquire their owner from origin and must not depend on current Catalog visibility.

### D2 — Cursor authentication without duplicating cryptography

Use the existing Platform-backed ASP.NET DataProtection candidate with a journal-specific purpose chain. Separate list and history purposes and protocol version1; bind protected payload to resolved account and schema version. List payload includes normalized supported filter fingerprint, date/UUID sort keys and issued/expiry UTC timestamps; history adds EntryId and beforeRevision. Default25/max100, maximum cursor lifetime24h, bounded encoded size2KiB. Validate token protection, version, expiry and all bindings before constructing the internal C2 cursor; reject uniformly with sanitized InvalidArgument. Page size can change within bounds and is not a filter. No offset/count dependency or private body inside a cursor.

**G2 unresolved configuration gate:** Customer has no DataProtection/persisted key registration. Before implementation admission, accept the key producer and persistence location, application/purpose isolation, multi-instance sharing and restart/rotation behavior. Reuse Platform Redis registration only when its package/config owner verifies availability. Keep retired keys decryptable until all still-valid cursors expire; emergency key revocation can invalidate tokens with the same InvalidArgument response. Do not use process-local production keys, new hard-coded HMAC secrets, another service's purpose/key scope or claim Redis deployment from source inspection. Isolated test keys can prove codec behavior; they do not prove deployed persistence.

### D3 — Copy extends request identity, not the receipt engine

Copy input selects owned SourceEntryId and explicit positive SourceRevision, chosen occurrence/date precision and an explicit unknown-target choice when fallback is required. No source public IDs, publication consent/intent or caller owner identifiers. First execution reads an ordinarily accessible owned immutable source revision, verifies its retained payload/profile integrity, copies bounded private content and uses the newly confirmed occurrence. A fresh copy of a deleted/foreign/missing source is NotFound. Unknown source can retain its owner-owned unknown reference; Product retention requires the unavailable EJ04 adapter. Owner-confirmed unknown fallback can copy an unavailable Product only as a private unknown label, without Catalog grants or facts.

Use C2 Create receipt storage and the same account+operation+key uniqueness/24h lifetime. Create and Copy intentionally share that namespace; a copy-intent discriminator, source entry/revision, chosen occurrence, trusted creation origin and explicit options are included in canonical request identity, so cross-method key reuse or changed source/date/options conflicts. Extend the owner-internal request-identity input in the existing atomic producer if necessary; do not implement a second receipt lookup/lock/hash algorithm or new rows. The immutable source revision identity binds its content; verify its hash on first execution. Retry comparison uses the normalized copy intent, not the mutable current source/header or caller-selected account.

**G3 producer acceptance gate:** the current command hashes the resolved mutation draft and has no Copy intent. Parent must accept this bounded producer extension and transaction sequence before runtime admission. Required sequence: resolve/lock owner lifecycle, compute normalized intent, match existing receipt through the shared producer, otherwise validate ordinarily readable source and create draft atomically. Matching replay must not reread the source private body. Source edits/deletion after successful copy do not create another destination or change the result. Missing/conflicting receipt cannot bypass source ownership/lifecycle/deletion checks. No schema change or new operation enum/check-constraint is inferred.

### D4 — Stable response projection and confidentiality

For successful Create/Update/Copy replay, use receipt EntryId+ResultRevision and that exact immutable revision/profile, not current mutable entry header. Build the entire personal DTO consistently from the committed revision; current-only metadata is not mixed into the original body. Keep the same entry/revision result even if later edits occur. Do not reconstruct a deleted private body for a retry. Every replay rechecks destination owner/lifecycle/deletion before returning a body. These stable retry guarantees apply within the existing24h receipt lifetime; expiry does not promise permanent deduplication. Delete returns Empty and its matching unexpired receipt can replay Empty after lifecycle check without serving history. CAS/idempotency-body conflict maps to Aborted; invalid typed input to InvalidArgument; foreign/missing personal resource to identical NotFound.

**P1 parent policy acceptance required:** an owner retry of Create/Update/Copy after destination deletion returns NotFound, despite a retained internal receipt. This prioritizes the accepted C2 deleted-serving prohibition over successful body replay after deletion. It does not erase/change the original receipt or promise success for every retry. A previously completed Copy may replay while its source has since been deleted if its destination remains ordinarily readable; this reuses the saved result, never grants a fresh source read. Parent must accept these visible semantics before implementation; do not silently change C2 or return a success tombstone DTO not defined in C3.

### D5 — Typed wire and additive protobuf compatibility

Create a new service/models alongside ProductCollection using fresh tags and existing Guid/Timestamp conventions. New numeric values use invariant decimal strings exactly representable as18,6; reject invalid, non-finite, exponential/lossy or out-of-range input rather than rounding. Use explicit presence for nullable score and clears; zero is invalid score, not null. OccurredDate is a calendar date, with DateOnly or LocalTime precision and nullable local time/IANA zone/UtcOffsetMinutes; preserve C2 tick precision and both DST choices. Do not manufacture midnight or use CreatedAt as occurrence. General freezes empty definitions; typed observation RT03 uses an authorized frozen-profile fixture without enabling Product intake.

Validate known fields semantically: unknown enum values, absent required target/value, wrong known type/wire shape, invalid oneof selection or known repeated singular/oneof ambiguity are InvalidArgument. Preserve benign unknown-field acceptance needed by additive protobuf compatibility. **G4 parser gate:** the ordinary generated parser may collapse duplicate singular/oneof alternatives. The implementation design must name bounded known-field inspection at the owner ingress before data loss, without a new generic protobuf parser or banning benign future tags. Parse/size limits apply before domain mapping. Unknown fields must not grant permissions, silently select targets or enter canonical request identity as semantic data; reject unknown shapes only when malformed or beyond limits. Prove behavior with raw-wire fixtures and old/new generated clients; runtime acceptance cannot be inferred from a proto diff.

### D6 — Product fail-closed boundary

All new Product create, mapping/rebinding, Product-retaining Copy and Product-context profile resolution require the authoritative target adapter. At EJ03 its default is unavailable: authenticated valid requests return FailedPrecondition before Catalog/journal writes. The existing internal Product producer is never called as a fallback authorization adapter. Keep typed Product/map contract surface for future EJ04; do not manufacture target visibility or enable a Product writer now. Unchanged owned archived Product entry note/date/score edits, history/delete remain owner-safe under frozen retained semantics; any target/profile change invokes the blocked boundary. Unknown/General creation still requires G1 trusted origin.

### D7 — Package/version/release is an independent gate

Current Customer.Contracts1.10.0 remains unchanged in this docs MR. Additive1.11.0 is an unapproved candidate; the mandated version confirmation and proto preview precede future proto/version commit. Never assign final field numbers in this proposal. Generated owner/client builds, raw-wire compatibility, host auth tests, exact package/publish artifact and MR/main evidence are future RT03 gates. Upgrade owner package before later BFF/generated consumers, in separate owner tasks. Customer main CI also publishes/deploys the service image after contracts: future merge admission must explicitly cover that release/deploy boundary; Draft docs MR never arms auto-merge or publication.

## Risks / Trade-offs

G1/G2 are real producer/configuration gaps; defining protocol shape cannot authorize or provision them. G3 needs a bounded existing producer extension, which is not an implementation grant. P1 changes observable retry success after deletion and remains a parent-reviewed policy choice. G4 requires ingress evidence that generated messages alone cannot provide. Legacy double numeric precision is intentionally preserved; new wire cannot silently relabel it as decimal. A docs-only green CI or OpenSpec planning completion proves none of these runtime gates.
